# 多城市空气质量监测与智能问答 Agent

## 项目一句话

一个会调工具、会查标准、也会在证据不足时拒答的环境问答 Agent：基于 6 个城市 52,704 条小时级空气质量数据，组合 10 个 Tool、RAG 引用溯源、规则/LLM 双模式和全链路 trace。

## 项目背景

普通问答 Demo 通常只回答问题，却没有解决三件事：

- 答案是否真的调用了可靠的数据工具；
- 引用政策或标准时，条款是否真实存在；
- 工具选错或检索低置信时，系统能否拒绝回答，而不是编造内容。

这个项目把空气质量数据、预测模型、规则检索和 LLM Agent 组合成完整链路，并通过 60 条回归集验证工具选择能力。

## 系统架构

![空气质量 Agent 架构](public/projects/air-quality-agent/architecture.png)

系统支持两条 Agent 路径：

- 配置 LLM Key 时使用 LangGraph 编排工具调用；
- 未配置或 LLM 调用失败时自动降级为规则 Agent。

两条路径共享同一套 10 个工具、RAG 拒答逻辑、引用约束和 trace 记录。

| 工具 | 作用 |
| --- | --- |
| get_overview | 城市空气质量概览 |
| get_realtime | WAQI 实时数据，未配置时回退历史最新 |
| get_forecast | 未来 24h 预测与超标预警 |
| get_cities_comparison | 6 城市对比 |

| query_policy | 环保标准与政策条款 RAG 检索 |

## 三层幻觉控制

### 第一层：强制引用

涉及标准或政策的回答必须给出条款标题、条款编号和结构化 references，不允许只生成一段看着合理的文字。

### 第二层：低置信拒答

RAG 同时支持 Chroma 向量检索和零依赖关键词检索。

- 关键词后端阈值：0.15
- 向量后端阈值：0.53
- 阈值 0.53 来自真实校准：相关查询 top-1 相似度 0.557 到 0.851，无关查询 0.330 到 0.507

低于阈值时直接返回“未检索到相关标准条款”，避免模型编造编号。

### 第三层：数据约束

无检索场景下，回答只允许基于工具返回的结构化数据，不允许自由补充不存在的监测结论。

## 评测结果

![工具选择评测结果](public/projects/air-quality-agent/evaluation-summary.png)

评测使用同一套 60 条回归集，覆盖 10 个工具、6 个城市、4 类污染物和 12 条易混淆样本。

| 模式 | 基线 | 最终 |
| --- | --- | --- |
| 规则 Agent | 48/60，80.0% | 60/60，100% |
| LangGraph LLM Agent | 49/60，81.7% | 58/60，96.7% |

LLM 最终 2 条失分都来自 get_alerts 与 get_comprehensive_alerts 的语义边界，没有调用失败或 JSON 格式错误。

## 关键 Bug 与解决方案

### Bug 1：实时与告警意图冲突

现象：

“北京当前有哪些污染物超标告警”“深圳今天空气有哪些告警”被路由到 get_realtime，而不是细粒度告警工具。

原因：

实时分支过早 return，只要命中“当前”“今天”就不会继续检查告警意图；综合预警工具又吸走了“告警”类问题。

解决方案：

在综合预警和实时分支之间新增 get_alerts 专属路由，区分“当前阈值明细”和“综合预警中心”。含预测词的问题不会被拦截，继续走多工具并行。

### Bug 2：模型训练请求没有对应工具路由

现象：

“帮我训练北京的空气质量模型”“更新深圳的模型参数”落入默认概览工具。

原因：

规则引擎没有“训练 / 重训 / 建模 / 更新模型”等意图分支。

解决方案：

新增 train_models 路由，并将训练请求从普通查询中隔离，避免误触发数据查询。

### Bug 3：政策问题没有工具

现象：

“空气质量标准是什么”“PM2.5 国家限值是多少”只能返回概览数据。

原因：

最初工具集只有数据与预测，没有政策知识检索能力。

解决方案：

新增 query_policy 工具，连接 11 条环保标准与健康防护知识库；检索低置信时返回 refused=true，由 Agent 明确拒答。

### Bug 4：政策工具被错误追加数据概览

现象：

第二轮评测为 59/60。唯一错误是纯标准问题同时返回 query_policy 和 get_overview。

原因：

政策分支见到“多少”就追加数据概览，把“标准限值是多少”误判成数据查询。

解决方案：

只有同时出现明确城市和明确数据疑问词时才追加概览；纯标准问题只调用 query_policy。

结果：

第二轮 98.3% 提升到第三轮 100%。

### Bug 5：Prompt 修改造成回归

现象：

给 LLM 路由提示词增加“今天”关键词规则后，准确率从 96.7% 降到 95%。

原因：

新规则修好了一条告警问题，却引入了“今天 + 告警”的冲突，属于典型的修一题坏一题。

解决方案：

回滚该规则，保留稳定版本；剩余 2 条语义边界问题如实标注，而不是继续为了分数堆 Prompt。

### 已知边界：前端问答初始化竞态

现象：

如果页面脚本尚未完成初始化就触发发送，可能访问到尚未初始化的 chatHistory。

解决方案建议：

将聊天状态移动到脚本顶部，在初始化完成前禁用发送按钮，并在 sendChat 中增加状态检查。

## 可观测性与工程化

- 每条问答写入 SQLite：问题、城市、模式、工具调用、回答、token、延迟和错误。
- trace 写入异常不会影响主接口，跟踪失败只记日志。
- MCP 使用同一套工具实现，支持 stdio 和 streamable-http 两种传输。
- 每日 07:30 自动生成 6 城市 Markdown 日报，复用同一套工具链路。
- 未配置 LLM、embedding 或外部数据 Key 时，系统分别降级为规则 Agent、关键词检索和历史基座，不伪装成在线服务成功。

## 技术栈

Python、FastAPI、LangGraph、OpenAI 兼容接口、DeepSeek、Chroma、Qwen embedding、随机森林、Pandas、scikit-learn、SQLite、MCP、Docker、Chart.js。

## 项目边界

- 当前评测重点是工具选择准确率，不是通用问答质量。
- 规则版 100% 建立在固定回归集上，不能外推为所有自然语言表达都准确。
- LLM 版剩余 2 条属于工具粒度歧义。
- 多工具并行执行尚未进一步优化。
